# Feature Spec — 2026-08-23 — Kitchen Page

## Status

**Genuinely new — not in `0_PRODUCT_ROADMAP.md` at all (unlisted, not deferred).** No roadmap row, no prior spec, and no code anywhere in `src/app/words/` implements a "kitchen," a consumable ingredient inventory, or a cooking action. Flagged per `AI_CONTRACT.md §3` step 1; not itself a blocker, but nothing below is authorized to build yet — every schema/RPC/route item under Scope is a Section 2 boundary and needs explicit **"authorized"** before implementation begins, per `AI_CONTRACT.md §2`.

A visual mockup of this page (cupboard → ingredient grid, side-by-side stovetop + oven, a countertop recipe book, and four color-coded drag-to-organize shelves) was already built and iterated on as an Artifact in this conversation, using placeholder emoji art and invented demo recipes/ingredients (not real catalog data). This spec turns that mockup into a real proposal against the actual schema; the mockup itself is throwaway and authorizes nothing.

**Two things this spec depends on, called out up front:**

1. **Builds directly on `shop_ingredient_rewards`**, the append-only per-ingredient reward ledger shipped 2026-08-22 (`docs/feature-specs/2026-08-22-paragraph-quiz-ingredient-reward.md`). **Documentation gap found while researching this spec:** that table and its `reward_random_ingredients` RPC are not present anywhere in `0_ARCHITECTURE.md`'s Data Schema section (§3), even though the roadmap (§4) records it as shipped. Raising this per `AI_CONTRACT.md`'s "never silently reconcile" instruction rather than fixing it myself — `0_ARCHITECTURE.md` should gain a `shop_ingredient_rewards` schema entry alongside this feature's own new tables, in the same commit that implements this spec (`AI_CONTRACT.md §4`).
2. **The "purchased" half of the Cupboard depends on roadmap item F** ("Ingredient shopping for kids," `docs/feature-specs/2026-03-30-shop-ingredient-shopping.md`), which is still `📋 Planned` — a Draft spec, zero lines of code, and confirmed zero references to `shop_ingredient_purchases` anywhere in `src/` or `supabase/migrations/`. Until item F ships, "purchased" ingredients are literally always zero. This spec's Cupboard therefore reads only from `shop_ingredient_rewards` in Phase 1 (see Scope) and is written so item F can plug into the same aggregation later without a redesign.

**Design decisions already resolved** (2026-08-23, by explicit answer — the six items below were raised as Open Questions in the original draft and are no longer open):

1. **Route & nav**: `/words/shop/kitchen`, nav-labeled "Shop Kitchen," inserted immediately after the existing "Recipe Shop" (`/words/shop`) entry and before "Recipe Shop Admin" (`/words/shop-admin`) in `getNavItems()` (`src/app/words/shared/words.shared.utils.tsx` lines 99–100). Accessible to child and platform-admin sessions only — parents route-blocked, matching `/words/shop`.
2. **Cooking gate**: reuses `shop_recipe_unlocks` as-is, with no separate/parallel unlock mechanism — a recipe's cookable-and-unlocked state in the Kitchen is entirely decided by whatever is already unlocked on `/words/shop`'s own content. Confirmed as originally proposed.
3. **Ingredient economy**: the duplicates model is confirmed — `shop_ingredient_rewards` keeps allowing unlimited duplicate ingredients, never "collect each once." This is the precondition this spec's whole consumption mechanic depends on, and it resolves the 2026-08-22 ingredient-reward spec's own still-open Question 1 the same way; that spec's Open Questions section should be updated to reflect this when this spec is implemented.
4. **Re-cook limits**: no cap. A recipe may be cooked as many times as the child has ingredients for.
5. **Drag-and-drop**: must work by touch on iPads and phones, not mouse-only — this is a scope change from the original draft (which had deferred touch support as a follow-up) and requires a different implementation approach than the reviewed mockup's native HTML5 drag-and-drop; see Proposed Behavior → Shelves.
6. **Parent visibility**: none, confirmed — matching `/words/shop`'s existing parent-blocked posture.

## Problem

Today, a rewarded ingredient (`shop_ingredient_rewards`) is granted once, shown once in the paragraph-quiz reward panel, and then never seen again — per that spec's own Out of Scope list, "there is no page anywhere in the app where a child could look back at what they've collected." Separately, `shop_recipes` can be *unlocked* with coins (revealing its ingredient list for inspection), but nothing in the app lets a child ever *do* anything with an unlocked recipe or a collected ingredient — there is no concept of spending an ingredient, "making" a dish, or a child-owned collection of finished dishes. The request is a new `/words`-workspace page, visually a kitchen, where a child can (1) see everything they've collected in a cupboard, (2) cook an unlocked recipe on a stovetop or in an oven by spending the ingredients it needs, and (3) see their finished dishes displayed on shelves they can organize into categories.

## Scope

**Phase 1 (this spec):**

- **New route** `/words/shop/kitchen`, nav-labeled "Shop Kitchen" and positioned immediately after "Recipe Shop" in the nav — child + platform-admin only, matching `/words/shop`'s existing role gate (`Recipe Shop Rules` rule 1, `permissions.ts` `case '/words/shop': return role === 'child'`). Parents are route-blocked, consistent with every other purely-play/reward surface in the app. (See Status → Design decisions already resolved, item 1.)
- **Cupboard**: a clickable cupboard that opens to a grid of every ingredient the child has ever been rewarded, aggregated by `ingredient_key` (count = number of matching `shop_ingredient_rewards` rows minus everything already spent — see Consumption ledger below). No purchased-ingredient source yet (see Status).
- **Recipe Book**: a clickable book that opens to a list of every **cookable** recipe (`shop_recipes.cook_method is not null`, see Schema) the child has already unlocked via `shop_recipe_unlocks` — the Kitchen introduces no separate unlock mechanism of its own; a recipe becomes cookable the moment `/words/shop`'s existing unlock flow marks it unlocked (Status item 2) — each showing its required ingredients and a computed ready/not-ready state against the child's current available counts. Un-unlocked cookable recipes show the existing locked-tile treatment and unlock flow already on `/words/shop` — this page does not duplicate or replace the unlock UI, it only reads `shop_recipe_unlocks`.
- **Stovetop + oven**: two clickable appliances. Selecting a ready recipe in the Recipe Book, then clicking the appliance matching that recipe's `cook_method`, calls a new `cook_shop_recipe` RPC that atomically spends the required ingredients and creates one cooked-dish record. Clicking the wrong appliance, or one with no recipe selected, is a client-side no-op with an inline message — no RPC call. No cap on how many times a recipe may be cooked (Status item 4).
- **Shelves**: four shelves — one default/unsorted shelf every newly-cooked dish lands on, plus three child-organizable, differently-colored category shelves (Drinks, Desserts, Hot Meals). Dragging a dish tile from any shelf onto another calls a new `move_shop_cooked_dish` RPC that updates that one dish's category. Cooking the same recipe again always bumps the existing tile's count in whichever shelf it currently sits in — it is never reset back to the default shelf (re-cooking must not undo a child's own organizing). **Drag-and-drop must work by touch (iPad/phone) as well as mouse** (Status item 5) — see Proposed Behavior → Shelves for the required implementation approach.
- **Shop Admin** (`/words/shop-admin`) gains one new field on the existing recipe edit form: `cook_method` (None / Stove / Oven). Recipes are cookable only once a platform admin sets this — existing recipes default to `null` (not cookable) until explicitly opted in. This is the only Shop Admin change; no other Shop Admin Rule is affected.

**New schema (all pending authorization):**

- `shop_recipes` gains one nullable column: `cook_method text check (cook_method in ('stove','oven'))`, default `null`. A recipe with `cook_method is null` is unlockable/inspectable exactly as today but never appears in the Recipe Book.
- New table `shop_ingredient_consumptions` — append-only ledger, one row per ingredient unit spent, mirroring `shop_ingredient_rewards`'s own shape and the codebase's established append-only-ledger convention (`quiz_sessions`, `shop_coin_transactions`, `coin_redemptions`, `shop_ingredient_rewards` are all insert-only). A child's available count of ingredient X is `count(shop_ingredient_rewards where ingredient_key = X) − count(shop_ingredient_consumptions where ingredient_key = X)`, computed client-side (matching this codebase's existing preference for client-side aggregation over ingredients/readiness — see item F's proposed-but-unbuilt `computeRecipeReadiness`) rather than a running-balance column.
- New table `shop_cooked_dishes` — one row per cooked dish (not aggregated server-side; the client aggregates by `recipe_id` for shelf display, the same count-badge pattern the mockup already uses). `shelf_category text check (... in ('default','drinks','desserts','hotmeal')) default 'default'` is the **one** field on any shop-adjacent table in this codebase that a child can update post-insert — a deliberate, called-out departure from the append-only convention everywhere else, because "drag to reorganize" is inherently a mutation, not an event log. It's still never touched by direct client UPDATE — only through the RPC below.
- New RPC `cook_shop_recipe(p_recipe_id uuid)` — **`security definer`, a deliberate departure from `unlock_shop_recipe`/`reward_random_ingredients`'s `security invoker` choice, caught and corrected during implementation** (the original draft of this spec proposed `security invoker` "matching precedent" — wrong, see below). Verifies caller role (child or platform admin), verifies `shop_recipe_unlocks` has a row for `(current_user_id(), p_recipe_id)`, verifies `shop_recipes.cook_method is not null` for the recipe, computes required ingredient quantities from `base_ingredients` (skipping entries without a resolvable `ingredientKey`, same skip-invalid-silently precedent as `reward_random_ingredients`), computes the caller's available count per required key, rejects with `insufficient_ingredients` (and which keys are short) if any required key falls short, otherwise atomically inserts one `shop_cooked_dishes` row and one `shop_ingredient_consumptions` row per required unit, and returns the new dish (recipe title/icon, for the UI to animate onto the shelf).
- New RPC `move_shop_cooked_dish(p_dish_id uuid, p_shelf_category text)` — same `security definer` correction as above. Verifies the dish belongs to the caller, verifies `p_shelf_category` is one of the four valid values, updates that one row, returns success/failure.

  **Why `security definer`, corrected from the original draft's `security invoker`:** `unlock_shop_recipe`/`reward_random_ingredients` pair `security invoker` with a matching defense-in-depth RLS insert policy scoped to the caller's own `user_id` — workable for them. But `shop_cooked_dishes`/`shop_ingredient_consumptions` are deliberately designed with **no RLS write policy at all** (see Schema below) — and RLS still applies inside a `security invoker` function body; it is not bypassed. A `security invoker` `cook_shop_recipe` would therefore fail its own `insert` at the RLS layer on every call. The only way to keep "the RPC is the only writer, full stop" true rather than aspirational is `security definer` (with `set search_path = public`, standard hardening against search-path hijacking). The alternative — adding a caller-scoped INSERT policy just to make `invoker` work — would let a child mint free cooked dishes via a direct Supabase client insert, bypassing the ingredient-spend check entirely, which this feature cannot accept. All of the RPC's own checks (role, unlock state, ingredient availability, dish ownership) still run before any write, exactly as they would under `invoker` — `security definer` changes who RLS sees as the writer, not what the function validates.
- New service functions in `src/lib/supabase-service.ts`: `listShopIngredientRewards(targetUserId?)`, `listShopIngredientConsumptions(targetUserId?)` (both plain reads — no such read path exists today; confirmed via `grep` that `supabase-service.ts` has no function reading `shop_ingredient_rewards` back out at all), `listShopCookedDishes(targetUserId?)`, `cookShopRecipe(recipeId)`, `moveShopCookedDish(dishId, shelfCategory)`.
- New domain helpers in `src/lib/shop.ts`: an ingredient-availability aggregator (rewards minus consumptions, grouped by key) and a cook-readiness helper analogous to item F's proposed `computeRecipeReadiness` but keyed to spendable availability rather than purchase completion — these are two different questions and should not share one function.

## Out of scope

- Purchased ingredients as a Cupboard source — blocked on item F shipping (see Status). This spec's aggregation helper is written so item F can add its own ledger as a second input later without changing the Cupboard's rendering code, but no purchase UI, table, or RPC is touched here.
- Any coin cost for cooking itself. Cooking spends ingredients only; it is not a second monetization surface layered on top of the existing coin-unlock gate. (Unlocking the recipe in the first place still costs coins, unchanged.)
- Un-cooking, deleting, or refunding a cooked dish. Once cooked, a dish exists forever (subject to the re-cook-bumps-count behavior above) — there is no "undo."
- Parent-facing visibility into a child's kitchen, cooked dishes, or ingredient spend. Matches this codebase's existing precedent of keeping shop-adjacent play surfaces child/platform-admin only (`/words/shop` itself is already parent-blocked).
- Any change to `shop_recipe_unlocks`, `unlock_shop_recipe`, or the existing `/words/shop` unlock flow. This spec only *reads* unlock state to gate the Recipe Book.
- Recipe authoring beyond the single new `cook_method` field — no new ingredient-catalog concepts, no new icon sets. Real ingredient/recipe art continues to resolve via `resolveShopIngredientIconPath`/`resolveShopRecipeIconPath`, never a new icon system.
- A cap on how many times one recipe can be cooked, or on total dishes per shelf.

## Proposed behavior

### Cupboard

Clicking the cupboard opens a modal grid, one tile per `ingredient_key` with `available > 0` (rewards minus consumptions), showing the real icon (`shop_ingredient_prices.icon_path` via `resolveShopIngredientIconPath`, exactly as `ShopSection.tsx` already resolves it — never a placeholder set, per the same rule the ingredient-reward spec already established), localized label, and current available count. An ingredient whose available count reaches 0 (fully spent) drops out of the grid rather than showing "x0" — matches this codebase's general preference for hiding rather than displaying zero-state rows where a filter is simpler than a disabled state.

### Recipe Book

Clicking the book opens a modal listing every recipe with `cook_method is not null`. For a recipe the child hasn't unlocked yet, the tile matches `/words/shop`'s existing locked-tile look and its only action is a link back to `/words/shop` to unlock it (no duplicate unlock button here — one unlock entry point). For an unlocked recipe, the tile shows its required ingredients against current availability and a Ready/Missing state, matching the mockup's copy pattern ("Missing: Salt").

### Cooking

Selecting a ready, unlocked, cookable recipe and then clicking the appliance matching its `cook_method` calls `cook_shop_recipe`. A wrong-appliance click or a not-ready recipe is caught client-side first (no wasted RPC round-trip) with an inline message naming the actual missing ingredients when relevant. On RPC success, the new dish animates onto the default shelf. On `insufficient_ingredients` (a legitimate race — e.g. two browser tabs, or the Cupboard view being stale), the client re-fetches availability and shows what's actually missing rather than a generic error, mirroring this codebase's existing "re-validate rather than trust stale client state" instinct (see `Due Review Queue Rules` rule 27's resume re-validation).

### Shelves

Four shelves render below/around the counter: **default** (every new dish's landing spot, never a drag target the recipe book routes to directly — only reachable by cooking or by dragging a dish back out of a category), **Drinks**, **Desserts**, **Hot Meals**, each visually color-coded. Dragging a dish tile onto a different shelf calls `moveShopCookedDish`; the count badge for that recipe on the source shelf decrements by one instance and the destination shelf's tile for that recipe increments (or a new tile appears if that recipe has no existing tile on the destination shelf) — one `shop_cooked_dishes` row moves per drag, not the whole aggregated stack.

**Touch support (Status item 5).** The reviewed mockup used native HTML5 `draggable`/`dragstart`/`drop`, which does not fire reliably on touch devices — unusable on the iPads/phones this needs to work on. The real implementation must use the **Pointer Events API** instead (`pointerdown`/`pointermove`/`pointerup`), which unifies mouse and touch input under one handler set rather than branching into separate mouse and touch code paths: `pointerdown` on a dish tile begins tracking and renders a dragged ghost element; `pointermove` repositions the ghost and hit-tests the shelf under the pointer via `document.elementFromPoint(x, y)`, highlighting it exactly like the mockup's `drag-over` state; `pointerup` commits the move (calling `moveShopCookedDish` if the pointer released over a different shelf) or cancels if released outside any shelf. `elementFromPoint`-based hit-testing during a pointer/touch move is not a new technique in this codebase — `ParagraphSpanSelector.tsx`'s touch-drag-select already does exactly this on `touchmove` (`0_ARCHITECTURE.md`, Add Paragraph Rule 6) — so this reuses an established pattern rather than introducing a new one or a third-party drag library. Dragged tiles need `touch-action: none` while a drag is active so the browser doesn't simultaneously try to scroll the page during the gesture.

## Edge cases

- **A recipe's `base_ingredients` entry has no `ingredientKey`, or references a key no longer in `shop_ingredient_prices`** — skipped from the required-ingredients computation (both for readiness display and for the RPC's actual spend), same skip-invalid-silently precedent as `reward_random_ingredients`.
- **Two browser tabs both attempt to cook the same recipe near-simultaneously** — the second `cook_shop_recipe` call re-checks availability inside its own transaction and can legitimately return `insufficient_ingredients` even though the client's last-known Cupboard state showed enough; the UI re-fetches and shows the real shortfall rather than a stale success.
- **A recipe is cookable (`cook_method` set) but the child hasn't unlocked it** — Recipe Book shows it locked; cooking is not offered; no RPC call is reachable from a locked tile.
- **A platform admin clears `cook_method` back to `null` on a recipe some children have already cooked** — existing `shop_cooked_dishes` rows for it are untouched (nothing here ever depends on `cook_method` after the fact); it simply drops out of the Recipe Book for future cooking.
- **A child has zero available ingredients of any kind** (new profile, or everything already spent) — Cupboard renders its existing empty state; Recipe Book shows every cookable-and-unlocked recipe as not-ready; no recipe is ever falsely marked ready.
- **Dragging a dish onto the shelf it's already on** — `moveShopCookedDish` is a client-side no-op (matches the mockup's existing `dish.shelfId === def.id` early return); no RPC call.
- **A dish is mid-drag when the child navigates away** — nothing is persisted until `drop` fires the RPC; an abandoned drag leaves the dish exactly where it was.
- **`cook_shop_recipe` fails entirely** (network/DB error) — no ingredients are consumed and no dish is created (the whole RPC is one transaction); the child sees an inline failure message and can retry, unlike the ingredient-reward RPC's "fail silently, never block" posture — cooking is a deliberate child action with a result the child is actively waiting on, not a background reward, so a real error here should be visible rather than swallowed.

## Risks

- **Two new RPCs need the same care `unlock_shop_recipe`/`reward_random_ingredients` already demonstrate**: role check, ownership check, no trusting client-submitted quantities for anything persisted. `cook_shop_recipe` in particular must compute required quantities and availability entirely server-side — a client that could claim "I have enough X" would let a child mint dishes for free.
- **Both RPCs are `security definer`, not `invoker`** (see Scope for why). Under `security definer`, RLS is not a backstop for anything these two functions get wrong — the function's own role/ownership/availability checks are the *only* line of defense, since the function runs with elevated privilege regardless of what the calling child's own RLS permissions would allow. Any future edit to either function's validation logic needs the same scrutiny a schema/RLS change would get, not the lighter scrutiny a typical `invoker` RPC might receive.
- **`shop_cooked_dishes.shelf_category` being mutable is a first for this codebase's shop-adjacent tables.** Get the RLS/RPC boundary wrong here and a child could plausibly rewrite another field, or another user's row — `move_shop_cooked_dish` must check ownership before any write, and no direct client UPDATE policy should exist at all (matching `shop_ingredient_rewards`'s existing default-deny-direct-write posture).
- **Client-side availability aggregation (rewards minus consumptions) means the Cupboard/Recipe Book must fetch both ledgers in full for the current user.** Fine at today's scale (a handful of reward events per quiz completion); worth revisiting if reward/consumption volume grows large enough to make per-load full-table reads expensive.
- **`scripts/verify-rls.ts` must gain new sections for both new tables** before this ships — default-deny-direct-write on `shop_cooked_dishes` (RPC-only for both insert and the one mutable field) and `shop_ingredient_consumptions` (RPC-only insert, no update/delete) are both easy to get subtly wrong.
- **Pointer-events-based drag is a real interaction to get right, not a drop-in.** `elementFromPoint` hit-testing during a fast drag on a small screen can miss a shelf boundary if the ghost element itself is under the pointer (it must have `pointer-events: none` while dragging, exactly as the ghost/dragged-item pattern requires); insufficiently generous shelf drop-target hitboxes on a phone-sized viewport would make organizing frustrating for a child. Needs real on-device testing (see Test plan), not just a desktop-browser touch-emulation check.

## Test plan

- RPC-level (`cook_shop_recipe`): role check rejects non-child/non-admin; rejects when the recipe isn't unlocked by the caller; rejects when `cook_method is null`; rejects with `insufficient_ingredients` (and correct missing keys) when any required ingredient is short; a normal case consumes exactly the required quantities and inserts exactly one `shop_cooked_dishes` row; concurrent double-submission cannot both succeed if there's only enough for one.
- RPC-level (`move_shop_cooked_dish`): rejects a dish the caller doesn't own; rejects an invalid `shelf_category` value; a normal case updates only that field on that one row.
- Domain: the availability aggregator correctly nets rewards against consumptions per key; the cook-readiness helper correctly separates ready/not-ready and names the right missing keys; both handle zero-reward and zero-consumption cases.
- Service: mocked-RPC unit tests for all five new service functions confirming request/response shape and snake_case → camelCase mapping (`0_BUILD_CONVENTIONS.md §6`).
- UI: Cupboard renders only available (`> 0`) ingredients with real icons; Recipe Book correctly locks un-unlocked recipes and shows accurate ready/missing state; clicking the wrong appliance or an unready recipe never calls the RPC; a successful cook animates onto the default shelf; a drag between shelves calls `moveShopCookedDish` with the right dish id and target category and never fires when dropped on the same shelf.
- Touch interaction: pointer-event simulation covering a full drag gesture (`pointerdown` → `pointermove` across a shelf boundary → `pointerup`) confirms the correct target shelf is hit-tested and `moveShopCookedDish` is called with it; a drag that ends outside any shelf cancels without calling the RPC; verify `touch-action: none` is applied to a tile only while actively dragging.
- **Manual on-device pass on an actual iPad and phone** (not just desktop touch-emulation) — this is the one interaction in this spec that automated tests can't fully cover, given the drop-target-hitbox and ghost-element concerns raised in Risks.
- `scripts/verify-rls.ts`: new sections for `shop_cooked_dishes` and `shop_ingredient_consumptions` — family-scoped read, RPC-only write, and (for cooked dishes specifically) that a client cannot UPDATE any field directly, only through `move_shop_cooked_dish`.
- **Live QA against a dev Supabase project**, per this codebase's now-consistent precedent (item I, the ingredient reward panel, the reveal-after-bounces hint all required and found real bugs during this step): cook a real unlocked recipe with a real ingredient shortfall and confirm the rejection; cook one successfully and confirm the shelf, Cupboard count, and both new tables all agree; drag a dish across all four shelves (by touch, on a real device) and confirm persistence across a reload.

## Acceptance criteria

- [ ] `/words/shop/kitchen` is reachable by child and platform-admin sessions only; parents are route-blocked, matching `/words/shop`; the "Shop Kitchen" nav entry appears immediately after "Recipe Shop."
- [ ] The Cupboard shows every ingredient the child has been rewarded with `available > 0`, using real `public/ingredients/*.png` icons via the existing resolver, and reflects consumption after a cook.
- [ ] The Recipe Book lists only recipes with `cook_method` set; un-unlocked ones are locked with a path back to `/words/shop`; unlocked ones show accurate ready/missing state.
- [ ] Cooking a ready recipe on its matching appliance spends exactly its required ingredients (never more, never less) and produces exactly one new dish, landing on the default shelf.
- [ ] Cooking the same recipe again bumps the existing dish's count wherever it currently sits, never resetting it back to the default shelf.
- [ ] Dragging a dish between any of the four shelves persists across a page reload and updates only that dish's `shelf_category` — confirmed by both automated pointer-event tests and a manual pass on a real iPad and phone.
- [ ] `scripts/verify-rls.ts` passes for both new tables, including confirming no direct client write path exists outside the two RPCs.
- [ ] Shop Admin can set/clear `cook_method` on a recipe; recipes default to not-cookable.
- [ ] Live-QA checklist (see Test plan) completed against a dev Supabase project through the actual app UI.
